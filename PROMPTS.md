# Промпт-шаблоны для работы с 1C MCP Suite

Готовые формулировки задач для AI-агента, подключённого к этому набору MCP-серверов.
Шаблоны рассчитаны на то, что агент умеет ходить в `mcp-platform-help`,
`mcp-code-templates`, `mcp-code-rag`, `mcp-bsl-checker`, `mcp-metadata-graph`,
`mcp-query-builder`, `mcp-testing`, `mcp-rest-proxy` и `1c-orchestrator`.

## Принципы, общие для всех шаблонов

Хороший промпт для этого агента всегда содержит четыре блока:

1. **Контракт задачи** — вход, выход, краевые случаи. Без этого агент угадывает.
2. **Маршрутизация по MCP** — в каком порядке и куда смотреть за знаниями. Принцип:
   сначала шаблоны и существующий код, потом справка, потом написание с нуля.
3. **Стандарты** — стандарты разработки 1С, стиль кода, серверный/клиентский контекст.
4. **Формат ответа** — план, код, результат проверки, тесты. Чтобы не разбирать каждый
   раз разные структуры ответа.

Во всех шаблонах ниже явно запрещаю уточняющие вопросы. Это сознательно: для
понятной задачи лучше получить «разумное предположение, помеченное в плане»,
чем потратить tool-вызовы на диалог. Для действительно неоднозначных задач
этот запрет снимайте.

## 1. Чтение CSV-файла в таблицу значений

```
# Задача
Напиши функцию на BSL, которая читает CSV-файл и возвращает ТаблицуЗначений.

# Контракт
Сигнатура: ПрочитатьCSVВТаблицу(ПутьКФайлу, Параметры = Неопределено) Экспорт

Параметры:
- ПутьКФайлу: Строка — путь к файлу на сервере.
- Параметры: Структура с опциональными полями:
  - Разделитель            (Строка, ";")
  - Кодировка              (КодировкаТекста, UTF8)
  - ПерваяСтрокаЗаголовки  (Булево, Истина)
  - ТипыКолонок            (Соответствие: ИмяКолонки -> ОписаниеТипов, пусто = Строка)
  - ЭкранированиеКавычками (Булево, Истина)

Возвращает: ТаблицаЗначений.
- Если ПерваяСтрокаЗаголовки = Истина — имена колонок из первой строки
  (нормализация: пробелы -> подчёркивания, недопустимые символы убираются).
- Если Ложь — "Колонка1", "Колонка2"…
- Пустой файл -> пустая таблица без ошибки.

# Требования
- Только на сервере. Директива &НаСервере или экспорт из общего модуля «Сервер».
- Обработка ошибок: при проблеме с файлом или несоответствии числа колонок —
  ВызватьИсключение с текстом, содержащим номер строки.
- Парсер должен обрабатывать: экранирование двойных кавычек ("" -> "),
  переносы строк внутри полей в кавычках, пустые поля, BOM в начале файла.
- Никаких глобальных переменных.

# Стандарты
- Следуй стандартам разработки конфигураций фирмы «1С».
- Комментарии к функции по формату БСП (описание, параметры, возвращаемое, пример).
- Именование на русском, КаждоеСловоСБольшой.

# Маршрут работы
1. В mcp-platform-help — синтаксис ЧтениеТекста, ТаблицаЗначений.Колонки.Добавить,
   ОписаниеТипов.
2. В mcp-code-templates — есть ли шаблон «разбор CSV».
3. В mcp-code-rag — похожие функции чтения файлов в нашей кодовой базе
   (стиль должен совпадать с существующим).
4. После написания — через mcp-bsl-checker. Если есть диагностики, исправь.
5. Через mcp-testing сгенерируй тесты:
   - файл с заголовками и 3 строками
   - разделитель "," и поля в кавычках
   - пустая строка посередине
   - несуществующий файл (ожидаем исключение)

# Формат ответа
1. План (3-5 строк): что нашёл в справке/шаблонах/базе, какой подход выбираешь.
2. Код функции целиком.
3. Результат bsl-checker (должно быть «без диагностик»).
4. Сгенерированные тесты.

Не задавай уточняющих вопросов. Неясное — отметь в плане как предположение.
```

## 2. Добавление нового реквизита в справочник

```
# Задача
Мне нужно добавить в справочник «Контрагенты» новый реквизит «ИННДляКонтроля»
(Строка, длина 12, обязательный). При записи элемента справочника этот реквизит
должен валидироваться: длина 10 или 12 цифр, корректная контрольная сумма.

# Что нужно сделать
1. Показать изменения, которые требуется внести в метаданные (XML выгрузки
   или описание для редактирования через Конфигуратор).
2. Написать процедуру/функции валидации ИНН (общий модуль, серверный контекст).
3. Написать обработчик ОбработкаПроверкиЗаполнения для модуля менеджера
   (или модуля объекта — уточни, где правильнее по стандартам БСП).
4. Обновить форму элемента: индикация ошибки, сообщение пользователю.

# Маршрут работы
1. В mcp-metadata-graph — актуальная структура справочника «Контрагенты»:
   какие реквизиты уже есть, какие модули существуют, какие подсистемы
   его используют. Это нужно, чтобы не создать дубликат реквизита и не
   сломать существующие обработчики.
2. В mcp-code-rag — поиск по ключевым словам «ИНН», «Валидация», «КонтрольнаяСумма»
   по существующей кодовой базе. Если функция валидации ИНН уже где-то написана —
   переиспользуй, не дублируй.
3. В mcp-platform-help — процедуры ОбработкаПроверкиЗаполнения,
   Сообщение, СообщениеПользователю, где и когда они вызываются.
4. mcp-bsl-checker — после написания.

# Стандарты
- Валидация ИНН (контрольная сумма) — по алгоритму из налогового
  законодательства: разные веса для 10- и 12-значных ИНН.
- Сообщения пользователю — через СообщениеПользователю с привязкой к полю формы.
- Серверный код — в общем модуле с признаком «Сервер».
- Тексты сообщений — в НСтр(...) для поддержки локализации (если в проекте это принято).

# Формат ответа
1. Список изменений в метаданных (plain text, без XML если возможно).
2. Код общего модуля с функциями валидации.
3. Код обработчика проверки заполнения.
4. Код модуля формы (только изменения, diff-стиль).
5. Результат bsl-checker.
6. Тесты через mcp-testing: валидный 10-значный, валидный 12-значный,
   с неверной контрольной суммой, с буквами, пустая строка.
```

## 3. Написание отчёта на СКД

```
# Задача
Нужен отчёт «Продажи по менеджерам за период» на СКД.

# Контракт отчёта
Группировки: Менеджер → Контрагент.
Ресурсы: Количество, Сумма, СуммаСкидки, СуммаБезСкидки.
Параметры отбора: НачалоПериода, КонецПериода (обязательные),
                  Организация (необязательный), Менеджер (необязательный).
Источник данных: документы «РеализацияТоваровУслуг», проведённые, в рамках периода.
Вывод: табличный документ с итогами по менеджеру и общим итогом.

# Маршрут работы
1. В mcp-metadata-graph — посмотри:
   - реквизиты документа РеализацияТоваровУслуг (как лежат суммы, скидки, менеджер)
   - существует ли регистр накопления по продажам, где эти данные уже агрегированы
     (использовать регистр ПРЕДПОЧТИТЕЛЬНЕЕ, чем делать запрос по документам)
2. В mcp-query-builder — построй запрос к найденному регистру/документу.
   Используй виртуальную таблицу «Остатки и обороты» / «Обороты» если работаешь
   с регистром накопления.
3. В mcp-platform-help — секции СКД: схема компоновки данных, наборы данных,
   ресурсы, параметры, настройки по умолчанию.
4. В mcp-code-rag — похожие отчёты в нашей конфигурации (для стиля и консистентности
   с существующими отчётами).

# Что я жду
1. Текст запроса для набора данных СКД.
2. Описание схемы: поля, ресурсы, параметры, роли полей (Измерение/Ресурс).
3. Структура варианта отчёта по умолчанию: группировки, отборы, условное оформление.
4. Если нужна программная пост-обработка — код модуля отчёта.

# Стандарты
- Использовать регистры, а не документы, если регистр есть.
- В запросе — параметры периода через ПериодСекунд/ГраницаПериода, не через СРАВНЕНИЕ СТРОК.
- Предпочтительный формат числа в ресурсах: Число(15, 2) для сумм.

# Формат ответа
1. Какую таблицу/регистр ты выбрал в качестве источника и почему (1-2 строки).
2. Текст запроса.
3. Описание схемы СКД (поля, ресурсы, параметры — таблично).
4. Настройки варианта.
5. Код модуля (если понадобился).
```

## 4. Рефакторинг длинной процедуры

```
# Задача
В модуле ДокументМодульОбъекта_РеализацияТоваровУслуг есть процедура
ОбработкаПроведения — она выросла до ~400 строк и делает слишком много:
проверки, движения по 5 регистрам, вызовы внешних API, отправку уведомлений.

Нужен рефакторинг: разнести ответственность, вынести логически независимые куски
в общие модули или отдельные процедуры, но НЕ СЛОМАТЬ существующее поведение.

# Ограничения
- Поведение при проведении должно остаться 1-в-1. Никаких «улучшений логики по пути».
- Сигнатура ОбработкаПроведения не меняется (это обработчик события).
- Транзакционность сохраняется: если что-то падало с исключением и откатывало
  проведение — должно продолжать падать с тем же исключением.
- Нельзя менять структуру регистров, даже если кажется, что лучше.

# Маршрут работы
1. В mcp-code-rag — прочитай сам код этой процедуры (покажи мне её перед началом).
2. В mcp-metadata-graph — проверь, какие регистры она затрагивает и какие
   ещё обработчики на этот документ есть (чтобы не продублировать логику,
   которая уже вынесена в подписки на события).
3. В mcp-platform-help — если используются нестандартные методы, убедись,
   что ты их понимаешь правильно.
4. mcp-bsl-checker — после рефакторинга, обязательно.
5. mcp-testing — сгенерируй сценарные тесты проведения (Vanessa-стиль),
   чтобы было чем закрыть рефакторинг.

# Стандарты
- Декомпозиция по ответственности: проверки отдельно, движения отдельно,
  внешние эффекты (API, уведомления) — отдельно и в самом конце.
- Внешние эффекты (API, email) выносим в ДОЛГИЕ обработчики или в подписку
  после проведения, НЕ внутрь транзакции. Если сейчас они внутри — отметь это
  в плане как известное техдолговое место, но сам не чини (это уже изменение поведения).
- Приватные вспомогательные процедуры — в том же модуле, с префиксом как принято
  в проекте (посмотри в mcp-code-rag как называют такие процедуры).

# Формат ответа
1. Краткий разбор: какие логические части ты выделил в исходной процедуре
   (список с номерами строк).
2. План рефакторинга: что куда переезжает, какие новые процедуры/модули появляются.
3. Дождись моего подтверждения плана, не пиши код сразу.
4. После подтверждения — код в формате «было / стало» по каждой выделенной части.
5. Результат bsl-checker.
6. Сценарии тестов.

ЗДЕСЬ уточняющие вопросы разрешены: если план двусмысленный, лучше спроси.
```

## 5. Разбор ошибки из журнала регистрации

```
# Задача
В журнале регистрации у пользователя «Иванов И.И.» с 14:30 до 14:35 сегодня
валится серия ошибок «Поле объекта не обнаружено (Контрагент)» при проведении
документов ПоступлениеТоваровУслуг.

Нужно: понять причину, показать мне место в коде, предложить исправление.

# Маршрут работы
1. Через mcp-rest-proxy (если настроено подключение к живой базе) —
   посмотри последние документы этого пользователя за указанный интервал.
   ВНИМАНИЕ: rest-proxy в read-only, это нормально — ничего менять не нужно.
2. В mcp-metadata-graph — посмотри структуру ПоступлениеТоваровУслуг:
   есть ли реквизит Контрагент прямо на документе, или он берётся из договора?
3. В mcp-code-rag — поиск по строке «Контрагент» в модулях этого документа
   и связанных подписках/регламентных задачах. Ищи места, где к полю
   идёт обращение без проверки на Неопределено.
4. В mcp-platform-help — если нужен справочник по конкретному методу.

# Что я жду от тебя
1. Гипотезу о причине ошибки (1-2 абзаца).
2. Точное место в коде: файл, процедура, строка (на основе mcp-code-rag).
3. Предлагаемое исправление (код «было / стало»).
4. Как избежать таких ошибок впредь: проверка через ЗначениеЗаполнено или
   ЭтоЗначениеНеопределено, или архитектурная правка (если причина в метаданных).

# Чего делать НЕ нужно
- Не лезь в живую базу ничего менять. Только чтение.
- Не предлагай «переписать документ с нуля». Точечный фикс.

# Формат ответа
1. Гипотеза.
2. Данные, которыми ты её подтвердил (что увидел в базе / в коде / в метаданных).
3. Код фикса.
4. Рекомендация на будущее.
```

## 6. Комплексная задача через оркестратор

Для задач, которые явно не помещаются в один заход — «доработать подсистему», «реализовать
интеграцию с внешним сервисом», «переделать учёт X под новые требования». Такие задачи
имеет смысл сразу запускать через `1c-orchestrator`, чтобы Аналитик собрал контекст,
Кодер написал, Ревьюер проверил.

```
# Задача
Реализовать интеграцию с сервисом «Честный Знак» для маркировки товаров:
получение кодов маркировки, их резервирование под документ Реализация,
отправка отчёта о вводе в оборот.

# Это комплексная задача, запусти через 1c-orchestrator с полным циклом
# Аналитик -> Кодер -> Ревьюер (-> повтор если ревьюер нашёл проблемы).

# Входные условия
- Сервис: API «Честного Знака», REST, авторизация по токену, токен живёт 10 часов.
- Документация API — в workspace/docs/chestny-znak-api.pdf
  (если агент не видит файл, пусть скажет явно).
- Существующих интеграций с этим сервисом в конфигурации нет.

# Ограничения
- Токен хранить в константе с безопасным хранилищем (СохранитьЗначениеПараметраРаботыСервера
  или через константу с механизмом защиты).
- Все вызовы API — асинхронно, не блокируя пользователя. Если нужна синхронность
  (например, при проведении) — через механизм долгих операций.
- Обработка ошибок API: логирование в журнал регистрации с категорией «Интеграция.ЧестныйЗнак».

# Стандарты
- Следуй стандартам разработки и архитектуре БСП.
- HTTP-вызовы — через общий модуль ПолучениеФайловИзИнтернета или аналогичный
  (проверь через mcp-code-rag, что используется в проекте).

# Формат ответа (от оркестратора)
- Аналитик: структура решения, список новых объектов метаданных, общих модулей,
  подписок на события.
- Кодер: код объектов по порядку (сначала общий модуль API, потом подписки,
  потом UI если нужен).
- Ревьюер: список замечаний, оценка «готово / требует правок».
- Если «требует правок» — ещё один круг Кодер -> Ревьюер.

На весь процесс дай оркестратору до 15 итераций tool-use на каждого субагента.
```

## Хорошие привычки при работе с этим агентом

**Проси план перед кодом.** Это пара секунд, но раз из пяти план показывает,
что агент неправильно понял задачу — и ты ловишь это до того, как он потратит
10 tool-вызовов на неправильное решение.

**Явно называй MCP-сервера, когда важен порядок.** Без подсказки Claude может
написать из головы то, что нужно было взять из `mcp-code-templates`. С подсказкой —
полезет туда в первую очередь.

**Не проси «улучшать» код по пути при рефакторинге.** Лучше разбить на две задачи:
сначала чистый рефакторинг без изменения поведения, потом отдельно — улучшения.
Это безопаснее и легче ревьюить.

**Запрашивай bsl-checker явно.** Claude иногда забывает прогнать проверку,
особенно если задача выглядит простой. Одна строка «после написания —
через mcp-bsl-checker» гарантирует запуск.

**Для коротких задач — короткие промпты.** Не надо писать простыню для задачи
«переименуй переменную в функции». Шаблоны выше — для задач, где цена ошибки выше,
чем стоимость хорошо написанного промпта.

**Пополняй файл.** Когда встретишь задачу, которая повторится — добавь её сюда
как новый шаблон. Через полгода это сэкономит часы.
